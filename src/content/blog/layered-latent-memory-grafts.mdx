<Callout type="insight" eyebrow="Thesis">
  Layered latent memory grafts are a proposed family of small trainable modules attached to a frozen language model. The program starts with explicit retrieval and treats LoRA as an experimental scaffold for protocol, temporal, and modular-update behavior—not as the presumed final memory substrate. Falsifiable alternatives include sparse memory finetuning, representation grafts (ReFT), and memory-as-model systems; fuzzy consolidation moves into latent space only when experiments beat simpler baselines. Exact evidence stays external.
</Callout>

Large language models have a strange relationship with memory. They appear to know facts, but those facts are entangled in parameters. They can retrieve documents, but retrieval often behaves like an external search step rather than an integrated memory process. They can be fine-tuned, but new updates can overwrite old behavior or blur contradictions. They can use tools, but they often need prompt-level scaffolding to know when a tool is required.

This proposal asks whether an LLM can develop a more useful kind of memory:

```text
not exact recall of every fact
but a fuzzy latent map of prior experience
that helps the model know where to look, what to distrust, and when to retrieve evidence
```

A human memory analogy is useful, as long as it is not taken literally. A person often remembers that something was discussed, roughly where it happened, who was involved, and what kind of source would contain the exact detail. The exact detail may still require checking notes. The target system should behave similarly: conversations, documents, file edits, and tool traces are replayed offline to produce a better fuzzy representation, while exact evidence remains retrievable.

The eventual system looks like this:

```text
new conversations + documents + code edits + tool traces + corrections
  -> offline replay / dreaming
  -> train recent memory modules
  -> practice retrieval and tool use
  -> detect contradictions and stale assumptions
  -> consolidate stable patterns
  -> preserve exact evidence externally
  -> wake up with a better fuzzy map of the domain
```

The experimental program should not start with the full system. It begins with a retrieval ceiling on a versioned temporal corpus, then cheap adapter comparisons: protocol QLoRA, rank-matched single LoRA, fast/slow stacks, and—if LoRA underperforms—sparse memory finetuning or ReFT-style grafts. Stacked LoRA is one hypothesis in that ladder, not the default end state. Each stage must beat simpler alternatives before adding routing, dream replay, or a memory compiler.

## 1. Literature map

This proposal sits at the intersection of retrieval-augmented generation, tool-use training, parameter-efficient fine-tuning, model editing, routed adapters, mixture-of-experts, continual learning, temporal representation learning, meta-learning, and neuroscience-inspired consolidation.

### 1.1 Explicit retrieval as memory

Retrieval-augmented generation combines a parametric generator with non-parametric memory. RAG uses a retriever over external documents to improve knowledge-intensive generation while keeping evidence accessible ([Lewis et al., 2020](https://arxiv.org/abs/2005.11401)). REALM pretrains with a latent retriever and frames retrieval as a way to make knowledge access more modular and interpretable than pure parametric storage ([Guu et al., 2020](https://arxiv.org/abs/2002.08909)). RETRO scales retrieval-conditioned generation with a large external database, showing that explicit memory can substitute for some parameter count while retaining factual access ([Borgeaud et al., 2021](https://arxiv.org/abs/2112.04426)).

The retrieval literature supports one permanent design constraint for this proposal:

```text
exact evidence should remain external, inspectable, updateable, and citeable
```

A latent memory module can improve retrieval, routing, and fuzzy understanding. It should not replace source-grounded evidence for claims that require provenance.

### 1.2 Tool and retrieval behavior training

ReAct shows that reasoning and acting can be interleaved, allowing a model to inspect external sources while solving a task ([Yao et al., 2022](https://arxiv.org/abs/2210.03629)). Toolformer trains models to decide when to call APIs, what arguments to pass, and how to incorporate the result ([Schick et al., 2023](https://arxiv.org/abs/2302.04761)). Self-RAG trains adaptive retrieval and reflection behavior rather than retrieving blindly ([Asai et al., 2023](https://arxiv.org/abs/2310.11511)). RAFT fine-tunes models for domain-specific open-book QA with retrieved documents and distractors, teaching the model to use relevant evidence rather than memorize the corpus ([Zhang et al., 2024](https://arxiv.org/abs/2403.10131)).

This thread motivates the first stable adapter:

```text
Protocol LoRA = a small adapter trained to practice correct retrieval, tool use, evidence filtering, citation, and deferral
```

This adapter should not store volatile facts. It should teach the base model a durable memory-use protocol.

### 1.3 LoRA as a cheap memory experiment

LoRA freezes the base model and adds trainable low-rank side paths to selected linear projections:

```text
y = W x + B A x
```

The original LoRA paper showed that low-rank updates can adapt large models with far fewer trainable parameters than full fine-tuning ([Hu et al., 2021](https://arxiv.org/abs/2106.09685)). QLoRA makes this practical on consumer hardware by training LoRA adapters through a frozen 4-bit quantized model ([Dettmers et al., 2023](https://arxiv.org/abs/2305.14314)).

For this proposal, LoRA plays two roles. First, it is an experimental proxy for memory: fast and slow LoRAs can test whether different update speeds help. Second, it is a stable interface mechanism: protocol and temporal LoRAs can teach the model how to use memory even when the corpus-specific memory changes.

LoRA is not a separate layer above the model. It is a trainable side-path inside the model's existing computations. Multiple LoRAs can be stacked additively:

```text
y = W x + ΔW_protocol x + ΔW_temporal x + ΔW_fast x + ΔW_slow x
```

Stacked LoRA remains an important falsifiable comparison—especially against a single rank-matched adapter—but recent work treats LoRA as a **scaffold** for protocol and temporal behavior, not necessarily the best substrate for continually updated fuzzy memory ([Understanding LoRA as Knowledge Memory](https://arxiv.org/abs/2603.01097); [Sparse Memory Finetuning](https://arxiv.org/abs/2510.15103)).

### 1.4 Model editing and side memory

ROME and MEMIT show that factual associations can sometimes be edited inside transformer weights ([Meng et al., 2022](https://arxiv.org/abs/2202.05262), [Meng et al., 2022](https://arxiv.org/abs/2210.07229)). These methods are valuable because they probe where factual associations live, but direct editing faces locality and generalization problems.

SERAC uses an explicit edit memory and learns when to apply edits ([Mitchell et al., 2022](https://arxiv.org/abs/2206.06520)). WISE is especially relevant because it introduces a main memory, a side memory, and a router for lifelong model editing, arguing that pure parametric editing and pure retrieval both fail different parts of the reliability/locality/generalization tradeoff ([Wang et al., 2024](https://arxiv.org/abs/2405.14768)).

This proposal inherits the side-memory view:

```text
base model = stable prior
memory adapters / grafts = side memory
router = learned control over memory paths
retriever = exact evidence path
```

### 1.5 Routed LoRA, adapter banks, and latent experts

ELDER uses multiple LoRAs plus routing for lifelong model editing, with a deferral route to preserve base ability ([Li et al., 2024](https://arxiv.org/abs/2408.11869)). AM-LoRA learns an attention mixture over LoRA modules for continual learning ([Liu et al., 2024](https://arxiv.org/abs/2409.19611)). MiLoRA routes among LoRA experts at prompt level to reduce generation-time overhead ([Zhang et al., 2024](https://arxiv.org/abs/2410.18035)). SoLA encapsulates edits as independent LoRA modules activated by semantic routing, enabling rollback by removing modules from routing ([Luo et al., 2026](https://arxiv.org/abs/2603.11239)).

This literature makes a bank of corpus-specific LoRA memories plausible:

```text
base model
  + stable behavior LoRA
  + protocol LoRA
  + temporal LoRA
  + corpus memory LoRA A
  + corpus memory LoRA B
  + corpus memory LoRA C
  + latent router
```

The router should be trained and evaluated separately. Adapter composition alone does not guarantee good memory behavior.

### 1.6 MoE and the temptation to put everything in latent space

Mixture-of-Experts models route tokens or sequences to sparse expert modules. Switch Transformers, GLaM, and DeepSeekMoE show that conditional computation can scale model capacity while activating only part of the model at inference ([Fedus et al., 2021](https://arxiv.org/abs/2101.03961), [Du et al., 2021](https://arxiv.org/abs/2112.06905), [Dai et al., 2024](https://arxiv.org/abs/2401.06066)).

This work reflects a broader tendency in modern model design: routing, compression, memory, and computation are increasingly moved into latent space. That instinct is useful. It should be applied gradually.

A memory expert inside MoE is an interesting later experiment. It is not the right starting point. MoE would add routing collapse, load balancing, expert starvation, and systems complexity before the adapter-memory hypothesis has been tested. A dense model with routed LoRA banks can simulate the relevant memory-routing question with fewer confounds.

### 1.7 Continual learning, plasticity, and learned update rates

Continual learning studies the stability-plasticity problem: a model must learn new information without overwriting old information. EWC slows updates to weights important for prior tasks ([Kirkpatrick et al., 2016](https://arxiv.org/abs/1612.00796)). Progressive Neural Networks freeze old columns and add new capacity ([Rusu et al., 2016](https://arxiv.org/abs/1606.04671)). Replay methods rehearse old examples while learning new ones.

The early fast/slow LoRA experiment hand-defines plasticity. The later research target is stronger:

```text
learn which layers, ranks, adapters, and memory modules should update
learn how much they should update
learn when to keep information external instead of consolidating it
```

This becomes a learned plasticity problem rather than only an adapter-composition problem.

### 1.8 Learning time

Time should not remain a hand-coded hyperparameter. Time2Vec learns vector representations of time with periodic and non-periodic components ([Kazemi et al., 2019](https://arxiv.org/abs/1907.05321)). Time-aware language models train on timestamped text to represent facts as temporally scoped rather than timeless ([Dhingra et al., 2021](https://arxiv.org/abs/2106.15110)). Know-Evolve, diachronic embeddings, and Temporal Graph Networks model entities and graph states that change over time ([Trivedi et al., 2017](https://arxiv.org/abs/1705.05742), [Goel et al., 2019](https://arxiv.org/abs/1907.03143), [Rossi et al., 2020](https://arxiv.org/abs/2006.10637)).

For this proposal, time means more than date:

```text
recency
validity
volatility
source authority
stale vs current
planned vs accepted
conversation order
project state
historical query intent
```

The temporal-gated LoRA phase tests whether the model can learn a latent time coordinate that controls adapter activation and retrieval behavior.

### 1.9 Temporal benchmarks

TemporalWiki evaluates whether models can acquire updated knowledge while retaining old knowledge across Wikipedia/Wikidata snapshots ([Jang et al., 2022](https://arxiv.org/abs/2204.14211)). StreamingQA evaluates timestamped news QA over time ([Liška et al., 2022](https://arxiv.org/abs/2205.11388)). PAT-Questions studies present-anchored questions whose answers depend on the current date ([Chen et al., 2024](https://arxiv.org/abs/2402.11034)).

These benchmarks motivate metrics that ordinary QA misses:

```text
current-state accuracy
as-of-time accuracy
new update acquisition
old valid fact retention
stale-fact suppression
source support
retrieval recall
contradiction handling
```

### 1.10 Neuroscience as design prior

Complementary Learning Systems theory separates fast hippocampal-like episode learning from slower cortical structure learning ([Blakeman and Mareschal, 2019](https://arxiv.org/abs/1905.02636)). Benna and Fusi model memory as interacting fast and slow variables, where new information enters fast variables and stable structure transfers to slower variables over time ([Benna and Fusi, 2015](https://arxiv.org/abs/1507.07580)). Hippocampal replay and sharp-wave ripples are associated with consolidation during rest and sleep. Predictive coding frames perception and memory as part of a system that maintains a model and updates on prediction error.

### 1.11 Recent anchors (2025–2026)

Several 2025–2026 papers sharpen the design space without replacing the historical spine above.

**Understanding LoRA as Knowledge Memory** ([arXiv:2603.01097](https://arxiv.org/abs/2603.01097)) studies LoRA as modular parametric memory: storage capacity, composability, and interaction with RAG. It supports using LoRA for **memory-use protocol** and temporal cues while keeping exact facts in retrieval.

**Continual Learning via Sparse Memory Finetuning** ([arXiv:2510.15103](https://arxiv.org/abs/2510.15103)) updates only highly activated memory slots on memory-layer models and reports far less forgetting than full fine-tuning or LoRA at matched acquisition. If this holds on temporal agent tasks, sparse memory—not stacked LoRA—may become the primary fuzzy substrate; LoRA would teach *how* to use memory.

**ReFT** and **CS-ReFT** ([arXiv:2404.03592](https://arxiv.org/abs/2404.03592), [arXiv:2503.10617](https://arxiv.org/abs/2503.10617)) intervene on hidden states with low-rank or routed subspaces instead of weight deltas. They are a natural test for temporal/source-scope grafts before committing to large adapter stacks.

**MemoryAgentBench** ([arXiv:2507.05257](https://arxiv.org/abs/2507.05257)) and **MemGym** ([arXiv:2605.20833](https://arxiv.org/abs/2605.20833)) evaluate memory through incremental multi-turn interaction and long-horizon agent regimes (tool use, research, coding). They motivate moving from static QA to harnesses that score retrieval, test-time learning, and selective forgetting together.

**MeMo** and related memory-as-model work ([arXiv:2605.15156](https://arxiv.org/abs/2605.15156)) keep the base LLM frozen while a specialist memory model holds cross-document structure. That path is a deliberate foil: grafts integrate inside the base model’s computation; MeMo externalizes memory entirely.

```text
rank-matched single LoRA
  vs fast/slow LoRA
  vs temporal-gated LoRA
  vs sparse memory finetuning
  vs ReFT temporal graft
```

If temporal-gated LoRA cannot beat a rank-matched single LoRA, the layered-LoRA stack is probably overbuilt. If sparse memory finetuning wins clearly, LoRA should remain the protocol layer, not the main memory store.

## 2. Core hypothesis

The working hypothesis is:

<Callout type="insight" eyebrow="Hypothesis">
  A frozen dense LLM augmented with modular grafts (LoRA, sparse memory slots, or representation interventions) can learn from evolving corpora more efficiently than full fine-tuning and more adaptively than pure retrieval, if exact evidence remains external while fuzzy temporal structure, retrieval priors, and update behavior are learned in latent space—only where they beat explicit retrieval and rank-matched single-adapter baselines.
</Callout>

The research program has three nested claims:

1. **Stacked modular adapters should beat single adapters** on evolving-memory tasks when rank and training budget are controlled.
2. **Latent routing and temporal gating should beat hand-defined adapter roles** once the system has enough supervision from synthetic and real update streams.
3. **Offline replay should improve future retrieval and project-continuity behavior** by training both fuzzy memory and the model's retrieval/tool-use policy.

The project should be allowed to fail early. If stacked LoRA cannot beat a rank-matched single LoRA, there is little reason to build a memory compiler. If temporal-gated LoRA cannot beat hand-defined fast/slow LoRA, learned time should not be assumed. If dream replay improves latent recall but worsens source discipline, the method is unsafe for evidence-grounded work.

## 4. Architecture ladder

The architecture is a ladder rather than a single design. Each level replaces a manually specified behavior with a learned one.

```text
Level 0: Base + RAG (measured ceiling)
Level 1: Protocol LoRA + RAG
Level 2: Stacked LoRA (falsifiable; not assumed end state)
Level 3: Fast/slow consolidation
Level 4: Learned temporal-gated LoRA or ReFT temporal graft
Level 5: Routed corpus LoRA bank
Level 6: Sparse memory finetuning + protocol LoRA + RAG
Level 7: Offline dream replay over real agent traces
Level 8: Separate latent memory module
Level 9: Memory compiler
Level 10: Learned plasticity field
Level 11: MoE memory expert (only if dense grafts justify it)
```

## 5. Experiment progress (first slice)

The [autoresearch-llmg](https://github.com/haowjy/autoresearch-llmg) harness is running the staged program above. **Phase 0 (canonical)** is experiment **P0-TW-03** on [TemporalWiki drift (easy)](https://huggingface.co/datasets/saxenan3/temporalwiki-drift-cl-easy): a versioned wiki corpus (~1004 `doc_id` slices), acquisition split (`test`) and retention split (`stable`), with **subject** recall@5 and **temporal** recall@5 (gold hit whose `last_edited` matches the question’s as-of date). Gate 0 (RAG ceiling) passed on corpus **v2** (May 2026).

Early exploratory runs **P0-TW-01** and **P0-TW-01b** used a collapsed subject index (~329 docs) and are **deprecated**—their headline numbers are not comparable to v2 without re-baselining.

## 6. Datasets

That structure is why it is the first benchmark: metrics can separate “found the entity” from “found the slice valid at as-of *t*.”

## 7. Full research timeline

The timeline below is ordered by falsifiability. Early phases should use dense models and LoRA because they are cheap, controllable, and easy to ablate. MoE, learned plasticity, and memory compilers are later phases because they introduce additional confounds.

### Phase -1: Data inventory and privacy boundary

**Purpose.** Establish the real target domain before training anything. The most valuable real data is not generic documents; it is agentic work history: Claude Code sessions, Codex sessions, repository changes, docs, tool calls, user corrections, abandoned plans, and final project state.

**Input corpus.**

```text
agent conversations
terminal/tool traces
file diffs
commits
issues or TODOs
docs and READMEs
user corrections
failed attempts
final repository state
```

**Outputs.**

```text
project/session index
chronological split by project
source metadata
privacy/redaction rules
deduplicated conversations
conversation-to-file links
initial evaluation candidates
```

**Key decision.** The raw logs should not be used as plain next-token training data. They should be converted into memory episodes and retrieval/tool-use traces. The model should learn better memory behavior, not imitate messy transcripts.

**Go/no-go.** Continue only if the corpus can be split chronologically and linked to enough objective artifacts: files, commits, docs, or later corrections.

### Phase 0: TemporalWiki RAG floor (P0-TW-03) — Gate 0 passed

**Hypothesis.** A strong explicit-memory baseline is necessary before latent memory has meaning. If retrieval alone solves the task, memory grafts are unnecessary.

**Implementation (running).** Experiment [P0-TW-03](https://github.com/haowjy/autoresearch-llmg/tree/main/llmg/experiments/P0-TW-03) exports [TemporalWiki drift (easy)](https://huggingface.co/datasets/saxenan3/temporalwiki-drift-cl-easy) to filesystem/SQLite stores, runs a matrix of harness cells (BM25, hybrid BM25+dense, rg) and agent cells (shell search vs `search_hybrid`) on `google/gemma-4-E4B-it`, and logs structured agent traces. Corpus **v2** indexes ~1004 versioned `doc_id`s; metrics include subject recall@5, temporal recall@5, and answer scores against gold `object`.

**Status.** Gate 0 passed on corpus v2 (May 2026). Pinned baselines are in **§5 Experiment progress** above. Deprecated **P0-TW-01** / **P0-TW-01b** shakedown runs used a collapsed index and are kept only for archaeology.

**Failure condition.** If hybrid retrieval cannot find relevant evidence at acceptable temporal precision, adapter experiments lack a grounded target. The shell agent’s low temporal recall on `test` shows that problem is not fully closed by indexing alone—tool discipline and temporal scope still matter.

**Later Phase 0 extensions** (not yet primary): project conversations, commits, and custom repo corpora (Phase -1 inventory).

### Phase 1: Protocol LoRA for retrieval and tool discipline (P1-02 — next)

**Hypothesis.** A small adapter can improve the model's use of retrieval tools without storing the corpus in weights.

**Model target.** Start dense. Phase 0 uses `google/gemma-4-E4B-it`; Qwen3-4B and Gemma 3 4B remain secondary targets. SmolLM3-3B is useful for reproducible controls. Phi-4-mini is useful for a reasoning-oriented small model.

**Training data.** Generate traces from synthetic corpora and real project logs:

```text
user query
available tools
retrieval query
retrieved evidence / distractors
source filter
answer with citation
or deferral when evidence is insufficient
```

**Training objective.** Supervised fine-tuning with QLoRA on tool-call and answer traces.

**Baselines.**

```text
Base + RAG
Base + RAG + reranker
Base + protocol LoRA + RAG
```

**Metrics.**

```text
tool-call accuracy
retrieval-query quality
citation precision
answer support
unsupported-answer rate
distractor rejection
latency overhead
```

**Expected outcome.** The adapter should improve source discipline: it should retrieve when evidence is needed and defer when retrieval is insufficient.

**Failure condition.** If protocol LoRA increases confident unsupported answers, it should not be used as a memory layer. Retrieval discipline is more important than latent recall.

### Phase 2: Stacked LoRA composition

**Hypothesis.** Multiple small adapters with different roles can compose without unacceptable interference.

**Architecture.**

```text
base model
+ optional existing behavior LoRA
+ protocol LoRA
+ temporal LoRA
+ fast memory LoRA
+ slow memory LoRA
```

At this phase the adapters are manually activated. No router is used.

**Core question.** Can stacked LoRA beat a single rank-matched LoRA?

**Rank controls.** If the stack uses four rank-8 adapters, compare against one rank-32 adapter. If it uses rank-8 protocol, rank-8 temporal, rank-16 memory, compare against a single rank-32 adapter.

**Training order.**

```text
1. train protocol LoRA on retrieval/tool traces
2. train temporal LoRA on current/historical/stale/planned examples
3. train slow memory LoRA on stable initial corpus
4. train fast memory LoRA on recent update batch
5. evaluate all combinations
```

**Ablation grid.**

```text
base
base + protocol
base + temporal
base + fast
base + slow
base + protocol + temporal
base + fast + slow
base + protocol + temporal + fast + slow
single rank-matched LoRA
stacked LoRA + RAG
```

**Metrics.**

```text
adapter composition penalty
retrieval quality
stale-fact suppression
new update acquisition
old valid fact retention
project convention recall
general instruction-following retention
latency per active adapter
GPU memory per adapter
```

**Expected outcome.** The stack should improve memory behavior without degrading general behavior. The most important comparison is against a rank-matched single LoRA.

**Failure condition.** If a single rank-matched LoRA performs as well or better, the modular structure is not yet justified.

### Phase 3: Manual fast/slow LoRA consolidation

**Hypothesis.** A plastic fast adapter plus protected slow adapter can adapt to recent updates while preserving stable knowledge better than a single continually trained adapter.

**Architecture.**

```text
W' = W + ΔW_slow + ΔW_fast
```

**Training loop.**

```text
T0:
  train slow LoRA on stable initial corpus

T1..Tn:
  freeze slow LoRA
  train fast LoRA on new update batch
  evaluate current, historical, and stale-trap tasks

consolidation window:
  use base + slow + fast as teacher
  train slow_new to imitate stable teacher behavior
  include replay of old valid examples
  reset or decay fast LoRA
```

**Consolidation methods to compare.**

```text
no consolidation
teacher-student distillation
weighted fast-to-slow merge with SVD recompression
replay-only slow update
EWC-style penalty on slow adapter drift
```

**Rank experiments.**

```text
fast r=8, slow r=32
fast r=32, slow r=8
fast r=16, slow r=16
single rank-matched r=40 or r=32
```

Two hypotheses are plausible. Long-term memory may need higher rank because it accumulates more information. Or long-term memory may need lower effective rank because it stores compressed abstractions while exact detail remains in retrieval. Both should be tested.

**Metrics.**

```text
update success
retention
stale suppression
historical as-of accuracy
fast reset loss
slow drift
rank efficiency
training time per update
```

**Failure condition.** If fast memory does all the work forever and slow memory never absorbs useful stable behavior, the consolidation mechanism is ineffective.

### Phase 4: Synthetic temporal worlds

**Hypothesis.** Controlled synthetic worlds provide the cleanest way to evaluate temporal memory, contradiction handling, and source scope before using messy real data.

**World generator.** Create fake projects, stories, or organizations with structured hidden state.

```text
entities: people, projects, files, policies, releases
relations: owns, leads, depends_on, supersedes, knows, blocks
sources: memo, wiki, chapter, author note, plan, commit, conversation
status: canon, planned, stale, contradicted, accepted, uncertain
```

**Event templates.**

```text
role change
rename
policy update
deadline slip
architecture replacement
temporary exception
plan abandoned
fact contradicted
later source supersedes earlier source
actor learns information at time t
```

**Generated documents.**

```text
old memos
latest wiki summaries
planning notes
agent conversations
code comments
commit messages
retrospective notes
conflicting drafts
```

**Question buckets.**

```text
current-state QA
historical as-of QA
what changed between t1 and t2
which source superseded which
what is only planned
what is stale
what does actor X know at time t
where should the model retrieve evidence
```

**Purpose.** These corpora are not the final task. They create ground truth for evaluating later learned temporal gates, routers, and compilers.

### Phase 5: Learned temporal-gated LoRA

**Hypothesis.** The system can learn a latent temporal coordinate that gates LoRA activation by recency, volatility, validity, source status, and query intent.

**Architecture.**

```text
h = pooled hidden state(query_or_chunk)
z_time = TemporalEncoder(h, source_context)
g_l = sigmoid(MLP_l(z_time))
y_l = W_l x_l + g_l * LoRA_l(x_l)
```

**Training signals.**

```text
current vs historical query labels
stale-trap examples
planned-vs-accepted examples
source supersession pairs
paraphrase consistency pairs
retrieval-scope labels
answer/evidence losses
```

**Baselines.**

```text
single LoRA
manual fast/slow LoRA
fixed layer-depth schedule
learned temporal-gated LoRA
learned temporal-gated LoRA + replay
```

**Metrics.**

```text
current/historical separation
stale-trap accuracy
planned-vs-accepted accuracy
paraphrase route consistency
gate sparsity
gate diversity
adapter activation cost
rank-matched quality
```

**Expected outcome.** Learned gates should beat manual fast/slow routing on temporal tasks without overactivating all adapters.

**Failure condition.** If gates learn only keyword shortcuts such as “now” or “before,” the method has not learned memory-time. Test with paraphrases and implicit temporal queries.

### Phase 6: Routed corpus LoRA bank

**Hypothesis.** A bank of corpus-specific LoRAs can reduce cross-project interference and improve retrieval priors if a latent router selects the right adapters.

**Architecture.**

```text
base model
+ protocol LoRA, always active
+ temporal LoRA, always or usually active
+ corpus LoRA bank:
    project_site
    project_agent_memory
    project_resume
    project_research_notes
+ small hidden-state router
```

**Router options.**

```text
external MLP router over pooled hidden states
nearest-centroid router over query embeddings
small transformer router over prompt + metadata
router LoRA that reshapes hidden states before routing
text-emitting router that outputs adapter IDs as tool calls
```

**Training data.**

```text
query -> relevant project/corpus
query -> adapter set
query -> retrieval path
query -> answer with evidence
negative examples where memory should not activate
```

**Serving constraint.** Route once per request. Avoid token-level routing at this phase. Keep top-1 or top-2 adapters active.

**Baselines.**

```text
all adapters always active
manual project selection
single merged corpus LoRA
external retrieval only
routed LoRA bank
```

**Metrics.**

```text
adapter selection accuracy
quality per active adapter count
cross-project interference
latency
GPU memory
hot-swap overhead
wrong-adapter failure rate
```

**Failure condition.** If the router frequently activates the wrong corpus LoRA, memory becomes worse than retrieval-only. A bad router is more harmful than no router.

### Phase 7: Real agent-history benchmark

**Hypothesis.** Agentic work traces are a better memory benchmark than static documents because they contain intent, tool use, mistakes, corrections, and final state.

**Data.** Use Claude Code and Codex sessions from several projects, linked to repositories and documents.

**Chronological split.**

```text
train memory on sessions 1..N
evaluate on sessions N+1..M
```

**Task families.**

```text
retrieve the prior session relevant to a new request
identify the file likely involved in a requested change
recover a project convention from prior corrections
avoid a stale plan that was later abandoned
answer a project question with source evidence
choose whether to inspect repo, retrieve memory, or answer directly
predict which prior decision constrains the current task
```

**Ground truth sources.**

```text
later conversation success
final repository state
commits and diffs
user corrections
accepted docs
manual spot labels for a small validation set
```

**Metrics.**

```text
future-session task success
retrieval recall@k over prior sessions/files
source support
stale-plan suppression
project convention recall
correction reuse
latency
manual evaluation score
```

**Failure condition.** If memory improves lore-like QA but does not improve future project work, it is not useful enough for the target domain.

### Phase 8: Dream replay v0

**Hypothesis.** Offline replay over recent conversations, documents, and tool traces can improve future retrieval and memory behavior without training the whole model.

**Dream input.**

```text
recent sessions
retrieved sources
files touched
errors and corrections
accepted changes
abandoned attempts
new docs
```

**Dream outputs.**

```text
memory episodes
retrieval-practice examples
stale-trap examples
project-convention examples
source-supersession examples
adapter training batches
validation tasks
```

**Training during dream.**

```text
train fast LoRA or fast memory module on recent episodes
train protocol LoRA lightly on retrieval/tool traces
run replay of stable old examples
update retrieval index immediately
avoid consolidating uncertain facts
```

**Acceptance tests before update is kept.**

```text
held-out future-session proxy improves
old stable behavior does not regress
retrieval support remains high
unsupported-answer rate does not increase
stale-trap accuracy does not fall
```

**Baselines.**

```text
no dream
index-only update
train on raw transcript text
train on extracted memory episodes
train on retrieval-practice traces
train on both memory episodes and retrieval traces
```

**Efficiency metrics.**

```text
GPU-hours per dream cycle
number of examples generated
adapter update size
retrieval-index update time
validation time
inference latency after dream
```

**Failure condition.** If dreaming makes the model answer from latent memory instead of retrieving evidence when needed, the dream objective is wrong.

### Phase 9: Separate latent memory module

**Hypothesis.** A separate memory module can store a fuzzy project/domain state more cleanly than LoRA alone, while LoRA continues to teach the model how to use that memory.

**Architecture.**

```text
base LLM
+ protocol / temporal LoRA
+ external retrieval
+ latent memory module
```

The memory module should encode:

```text
where evidence probably lives
which projects and files are related
which prior decisions matter
which facts are current or stale
which conventions are stable
which memories are uncertain
```

It should not be responsible for exact citations.

**Implementation candidates.**

```text
gated residual MLP attached to hidden states
cross-attention over learned memory slots
temporal graph memory over project episodes
small recurrent memory module
LoRA bank acting as memory proxy
```

**Baselines.**

```text
stacked LoRA only
routed LoRA bank only
retrieval only
memory module + retrieval
memory module without retrieval
```

**Metrics.**

```text
future-session performance
retrieval query quality
source selection
fuzzy project-state QA
evidence support
memory-module activation interpretability
inference overhead
```

**Failure condition.** If the memory module improves unsupported recall but reduces evidence-grounded answers, it should not be used for factual claims.

### Phase 10: Memory compiler

**Hypothesis.** A meta-learned compiler can amortize the work of organizing a messy corpus into memory slots, adapter initializations, source weights, and training traces.

**Training loop.**

```text
for corpus C_i:
  reset corpus-specific memory
  compiler reads C_i
  compiler outputs initialization / gates / example weights / distilled traces
  train memory for k steps
  evaluate on hidden temporal and retrieval tasks
  update compiler from evaluation loss
```

**Compiler outputs to test.**

```text
memory slot initialization
source trust weights
temporal coordinates
contradiction clusters
retrieval query templates
example sampling weights
adapter initialization deltas
training schedule
```

**Practical simplification.** Do not start by having the compiler generate all weights. Begin with generated distilled traces and memory-slot initializations.

**Baselines.**

```text
random memory initialization
heuristic source weighting
LLM-extracted structured memory
compiler-generated traces
compiler-generated slots + traces
```

**Metrics.**

```text
adaptation speed
few-step performance
contradiction handling
source-status inference
transfer from synthetic to real project corpora
compiler compute cost
```

**Failure condition.** If a simple heuristic initializer performs as well as the compiler, the compiler is unnecessary.

### Phase 11: Learned plasticity field

**Hypothesis.** The system can learn where and how much to update, rather than using manually assigned fast/slow roles.

**Motivation.** Stacked LoRA is modular but discontinuous. It defines adapter roles by hand. A deeper memory system should learn a plasticity field over layers, ranks, modules, and sources.

**Formulation.**

```text
ΔW_l = Σ_i g_{l,i}(z) * B_{l,i} A_{l,i}
```

where `g` controls activation. During training:

```text
θ_{l,i} <- θ_{l,i} - α_{l,i}(z) * ∇θ L
```

where `α` is learned plasticity.

**Inputs to plasticity controller.**

```text
latent temporal coordinate
source reliability
contradiction signal
gradient statistics
retrieval support
replay frequency
user correction strength
```

**Baselines.**

```text
manual fast/slow LoRA
learned gates only
learned plasticity only
learned gates + learned plasticity
rank-adaptive LoRA
single rank-matched LoRA
```

**Metrics.**

```text
update placement accuracy on synthetic tasks
stability-plasticity tradeoff
rank utilization
catastrophic forgetting
source-grounded behavior
training stability
```

**Failure condition.** If the controller always updates the same components or refuses to consolidate, it has learned a shortcut rather than plasticity.

### Phase 12: MoE memory expert

**Hypothesis.** A memory expert can be integrated into a sparse expert architecture after the dense adapter route has demonstrated value.

**Variants.**

```text
shared memory expert
routed temporal expert
hybrid retrieval expert
side-memory expert selected by MoE-style router
```

**Why late.** MoE introduces load balancing, expert starvation, routing instability, and serving complexity. These confounds should be avoided until dense stacked/routed adapters show a real memory effect.

**Baselines.**

```text
dense + routed LoRA bank
MoE + normal experts
MoE + shared memory expert
MoE + retrieval expert
MoE + side-memory path
```

**Metrics.**

```text
quality per active parameter
routing load balance
memory-expert activation precision
latency
communication overhead
continual update cost
```

**Failure condition.** If a routed LoRA bank on a dense base matches the MoE memory expert, the MoE complexity is not justified for this research path.

### Inference rules

```text
route once per request, not per token
activate top-1 or top-2 memory adapters
keep protocol and temporal adapters small
retrieve only when evidence is needed
avoid loading adapters from disk mid-generation
compare every improvement against latency overhead
```

### Dreaming rules

```text
never fine-tune the full base model
train small adapters or memory modules
prefer extracted memory episodes over raw transcripts
always include replay of stable old examples
always test unsupported-answer rate before accepting an update
separate exact evidence updates from latent memory updates
```

## 9. Model targets

Initial experiments should use dense models. Dense models isolate the memory mechanism from sparse-routing confounds.

```text
Primary (Phase 0 agent): google/gemma-4-E4B-it
Secondary: Qwen3-4B, Gemma 3 4B
Control: SmolLM3-3B
Reasoning-oriented target: Phi-4-mini-instruct
```

MoE should enter only after dense experiments show that temporal gating, stacked adapters, or routed corpus LoRAs improve memory behavior.

## 11. Decision gates

The roadmap should have explicit gates.

```text
Gate 1:
  Protocol LoRA must improve retrieval discipline over base RAG.

Gate 2:
  Stacked LoRA must beat a rank-matched single LoRA or show a clear modularity advantage.

Gate 3:
  Fast/slow consolidation must improve retention or stale suppression over single LoRA + replay.

Gate 4:
  Temporal-gated LoRA must beat manual fast/slow roles on implicit temporal tasks.

Gate 5:
  Routed LoRA bank must improve quality per active adapter and reduce cross-project interference.

Gate 6:
  Dream replay must improve held-out future-session performance without reducing evidence support.

Gate 7:
  Memory module must improve retrieval-oriented fuzzy state, not replace citations.

Gate 8:
  Memory compiler must beat heuristic initialization on adaptation speed or quality.

Gate 9:
  Learned plasticity must beat hand-designed plasticity schedules.

Gate 10:
  MoE memory expert must beat dense routed-adapter baselines on quality per cost.
```

These gates keep the proposal from becoming a pile of plausible modules. Each module must earn its place.

## 12. Why this might work

The proposal is plausible because the pieces are individually supported:

```text
retrieval preserves exact evidence
LoRA enables cheap modular behavior changes
routed adapters suggest memory shards can be selected semantically
continual learning motivates fast/slow plasticity
neuroscience motivates replay and consolidation
agent logs provide process-rich training data
```

The strongest version of the idea is not a model that memorizes more. It is a model that learns a better retrieval-oriented latent state:

```text
this request resembles that prior project region
that convention was established after a correction
that plan was abandoned
that file is likely relevant
that claim needs source evidence
```

## 13. Why this might fail

<Callout type="alert" eyebrow="Risks">
  The most serious failure mode is not that the model fails to remember. It is that the model remembers too confidently without retrieving evidence. Any latent memory gain must be checked against source support and stale-fact suppression.
</Callout>

Likely failures:

```text
rank-matched single LoRA performs just as well
fast memory absorbs noise and never consolidates
slow memory consolidates stale plans too early
temporal gates learn keyword shortcuts
router activates the wrong corpus adapter
latent memory reduces evidence discipline
dream replay overfits to transcript style
synthetic corpora fail to transfer to real agent logs
inference cost grows with too many active adapters
memory compiler is more expensive than heuristic extraction
```

## 14. Relation to MeMo

MeMo, the paper that motivates part of this discussion, is a useful foil. Its central move is to encode new knowledge into a dedicated memory model while keeping the main LLM unchanged. That makes the memory plug-in compatible with closed models and avoids modifying the base LLM directly.

This proposal differs in where integration occurs:

```text
MeMo:
  memory as a separate specialist model
  base LLM queries memory externally

Layered memory grafts:
  retrieval stores exact evidence
  LoRA/grafts reshape the base model's memory behavior
  corpus memory may be latent, routed, and replay-trained
```

The open question is whether smaller LoRA/graft modules plus retrieval practice can capture some of MeMo's synthesis benefits while preserving more provenance and requiring less than training a separate memory model.

## 15. The smallest publishable experiment

The first publishable experiment should be narrow:

> Does stacked and temporally structured LoRA improve evolving-corpus memory over rank-matched single LoRA and RAG baselines?

Minimum setup:

```text
model: Gemma 4 E4B or Qwen3-4B (after P0-TW-03 RAG floor)
training: QLoRA
corpora: synthetic temporal worlds + one real project history
adapters: protocol, temporal, fast, slow
retriever: hybrid keyword + dense
baselines: RAG, single LoRA, single LoRA + replay, rank-matched LoRA
metrics: update, retention, stale suppression, evidence support, retrieval recall, cost
```

A successful result would justify learned temporal gates. A failed result would still be useful: it would show that simple retrieval or single-adapter training is sufficient for the tested setting.

## 16. Long-term target

The final target is a memory lifecycle for agentic systems:

```text
experience during work:
  conversations, documents, files, code edits, tool calls, corrections

immediate memory:
  context window and retrieval index

offline dream:
  extract episodes
  generate retrieval traces
  train fast memory
  test stale traps
  replay stable examples
  consolidate durable patterns

future use:
  fuzzy memory points to likely evidence
  tools fetch exact sources
  answers cite support
  unsupported claims are deferred
```

The research direction can be summarized as:

> Start explicit and modular. Treat LoRA as a scaffold, not the final substrate. Move control into latent space only after each explicit scaffold has produced measurable supervision—and after sparse memory or ReFT baselines have been ruled in or out. Keep exact evidence external. Let latent memory learn where to look, what changed, and how much to update.
