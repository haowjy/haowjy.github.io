# 75% of Reads Were Redundant

I've been running AI coding agents heavily since February: Claude Code, Codex, OpenCode, plus a [multi-agent orchestration engine](https://github.com/meridian-flow/meridian-cli) I built on top of all three. After a [particularly expensive overnight session](/blog/what-happened-to-my-tokens), I wanted to understand my usage at scale. Not just one bad spawn. Everything.

I wrote a script that pulls tool-call history from every session across all three harnesses. Claude Code stores sessions as JSONL. Codex has its own event format. OpenCode writes to SQLite. The script normalizes all three and extracts every file read: `Read` tool calls, `cat` and `sed` in bash, `grep` and `rg`. Then it tracks whether the agent had already seen that file earlier in the same session.

The dataset covers 4,339 sessions from February through May 2026, across a dozen models, three harnesses, and 30+ agent roles.

<StatHero value="75.1%" label="of file reads were redundant" detail="50,319 of 67,017 reads across 4,339 sessions" />

Three out of four file reads were repeats. In a single agent session, the agent would read a file, keep working, then read that same file again later.

## What Agents Actually Do All Day

The redundancy clusters into three behaviors.

**Read-edit-reread** is the biggest. An agent reads a file, edits it, reads it back. Interestingly, recent versions of Claude Code's Read tool now include an injected instruction: a warning not to re-read a file immediately after editing it, because Edit/Write would have errored if the change failed and the harness tracks file state. I found this by checking the [tracked system prompt history](https://github.com/Piebald-AI/claude-code-system-prompts). The instruction isn't hardcoded in the tool description. It's injected through a template variable (`ADDITIONAL_READ_NOTE`) that was made configurable in v2.1.91 on April 3, 2026, which means it could be model-dependent or feature-flagged. Anthropic clearly noticed the same pattern. My data likely spans sessions both with and without the instruction, and I can't distinguish which. Either way, I found 2,197 read-after-edit events across the dataset. The worst single session: 76.

**Delegation restarts context.** My setup spawns agents from agents. Each spawn starts a fresh context window. The parent read the files and knows what matters; the child starts blind and re-reads everything. This is the expected cost of delegation. Fresh context means rediscovery. The question is whether better context handoff (passing file contents in the spawn, pre-digested `.context/` files) can reduce how much the child needs to re-read.

**Compaction creates amnesia loops.** Agent fills context, compacts (lossy summary), forgets file contents, re-reads, fills context again. Sessions that compacted averaged 69 reads and cost $24.56. Sessions without: 12 reads, $2.18. One session compacted 29 times.

The explorer number is interesting on its own. 42% redundancy is high for a role that should read once and report. When I dug in, the problem was compaction: explorers filling their context window, compacting, losing the file contents they'd already read, and re-reading them. That's what led me to build the `.context/CONTEXT.md` system: pre-synthesized knowledge files colocated with the code. An explorer can understand a module in a few hundred lines of markdown instead of reading 20 raw source files. It also pushed me to change how I dispatch explorers: scope each one tightly to a single question, fan out multiple cheap spawns instead of one that tries to read everything. Both changes cut the compaction-driven re-reads significantly.

Codex agents had zero explicit re-reads, but they did have 5 inline verifications (read-back embedded in the same bash command) and 14 `git diff` checks. Claude agents had 5 re-reads out of 42 edits, plus 10 test runs as the verification step. Both harnesses produce agents that verify their edits. The difference is the mechanism: Claude Code's separate `Read`/`Edit` tools make verification a distinct tool call that my analyzer counts. Codex's bash-based editing lets verification happen inside the same command or through `git diff`, which makes it invisible to a tool-call parser.

The RAE gap is mostly a measurement artifact. A `git diff` after 12 edits is one command. Twelve separate `Read` calls after twelve `Edit` calls is 24 tool round-trips. The tool interface shapes what you can measure, not just what agents do.

I can't tell from this data whether newer models are better at this. The role assignment confounds everything. What I *can* say is that no model, on any harness, in any role, drops below 30% redundancy. Even the best case is still re-reading a third of its files.

As for the "don't re-read" instruction, it's a Claude Code injection, and RAE is only a meaningful metric on Claude Code (Codex agents verify through `git diff` and inline commands that my parser doesn't count). So the question is narrow: does the instruction reduce RAE on the one harness where RAE measures what it claims to?

I cut the Claude Code data at April 3, 2026, the v2.1.91 release date. Overall RAE drops slightly, from 21.1% before the release to 19.0% on or after it. But the role-controlled comparison points the other way: coder, architect, and reviewer all re-read more often after the cut.

## A Workspace Cache

After every edit, the full file contents get dumped back into the conversation history as part of the tool result. Then the model re-reads the file anyway, adding another copy. The problem is not only compaction. The conversation history becomes both an event log and a storage layer. Old file snapshots stay in the transcript, new snapshots get appended, and the model has to infer current state from whichever copy is latest.

The fix I want to eventually prototype: a workspace cache. An LRU of recently touched files, injected into the system prompt and kept up to date as the model works. When the model edits a file, the workspace copy updates automatically. When the model tries to Read a file that's already in the workspace, the harness returns a short acknowledgment instead of the full contents. The model already has the current version. No duplicate. No wasted tokens.

The analogy I keep reaching for is working memory: small, active, immediately available state for the task at hand. Conversation history is more like an episodic trace: useful context, but chronological, noisy, and full of old versions. The workspace cache would give the agent one authoritative current copy while the transcript records what happened.

<WorkspaceCacheDiagram />

The tradeoff is prompt caching. Stale reads in conversation history are already cached: cheap per-token, immutable. Updating a file in the system prompt invalidates the cache from that point forward, so every edit means paying full input cost on the system prompt instead of cached cost. But the model was re-reading the file after edits anyway, paying full input cost on the re-read. The workspace cache shifts where those tokens live, not whether you pay for them. It might actually help with editing, since the model always has the current file state instead of a stale copy from three tool calls ago. The real risk is bloat: a system prompt stuffed with file contents could get large fast. When a file gets pushed out of the LRU, the harness injects a notice into the conversation history so the model knows it no longer has that file's contents and needs to re-read if it wants it back.

Tool-call metrics can't measure this. The transcript audit showed they miss half the file access patterns. So the measurement runs at the filesystem level: mount the workspace through [LoggedFS](https://github.com/rflament/loggedfs), a FUSE overlay that transparently logs every file operation with timestamps and paths. The agent works normally on top of it. Every access gets logged regardless of whether it came from a `Read` tool call, `cat`, `sed -n`, `git diff`, or an inline bash pipeline.

From the log, you build a per-file access timeline: written at T1, read at T2, written at T3, read at T4. The pattern is harness-agnostic.

- Baseline: same tasks, no cache, LoggedFS logging all file access
- Treatment: same tasks, workspace cache active, same LoggedFS setup
- What to watch: total filesystem-level reads, unique files vs. repeated access, tokens per session, compaction count, task success
- What could go wrong: system prompt bloat if too many files are cached, models confused by the short acknowledgment instead of full contents
