# What Happened to My Tokens?

The Codex $200 plan (20x) was so freeing. For weeks I could barely use half of it. Then one night I moved my full workflow over to Codex, and by morning half the plan was gone.

I'm building [meridian-cli](https://github.com/haowjy/meridian-cli), a multi-agent orchestration engine that sits on top of Claude Code, Codex, and OpenCode. Agents spawn agents: a product lead spawns a tech lead, which spawns coders, reviewers, and smoke-testers. Each spawn gets a fresh context window. That night the job was a major architecture refactor, and meridian-cli ran 198 spawns over about eight hours while I slept.

My Codex usage went from about 60% remaining to about 10%.

So I pulled the session data apart. I wrote scripts that read tool-call history from every spawn and estimate its cost at API rates. Three spawns stood out. All three were qa-leads, all ran on Codex, and all cost far more than the work they did.

The worst one cost $11.10. It pushed 20.9 million input tokens through GPT 5.4 in 36 minutes and wrote 26,000 tokens of output, an 800:1 ratio. It never delegated to an explorer. It read files itself, spawned 7 coders and 2 reviewers, then spent most of its budget polling for their results: 36 spawn-wait cycles, each one a full round-trip through its context window.

## What I Fixed First

I suspected the explorers before I suspected qa-lead.

Explorers are supposed to be the cheap reading layer. Some of mine were compacting over and over, losing their working state, and coming back with reports that looked incomplete. If the reading layer can't hold on to its own reading, every agent above it pays.

I changed two things. First, explorers now start from synthesized project knowledge instead of raw source: `AGENTS.md` and `.context/CONTEXT.md` files colocated with the code, covering architecture, module contracts, and past decisions. I'm not sure the colocated files were essential; a prompt that pointed explorers at my existing knowledge base might have done as well. Second, I tightened the explorer description to one module or one question per spawn. Broad "go understand this area" prompts were exactly how explorers ended up in compaction churn.

The next explorer run cost $0.11, didn't compact, and wrote a better report. That number flatters it. Keeping the inline context current cost another $0.66 in code-mirror agents, so the fair figure is $0.77. Still cheaper than before.

qa-lead was a suspect too. Codex orchestrators had a habit of spawning a child and then poking around instead of waiting. That's why the spawn instructions had become blunt: every background spawn must be drained with `meridian spawn wait`, and when wait yields, call wait again immediately.

Cheaper explorer, tighter scope, explicit wait instructions. I thought that covered it.

## Why Waiting Costs Money on Codex

When a Claude Code agent calls `spawn wait`, it blocks. One tool call, the agent sleeps, one result comes back when the child finishes.

Codex works request-response. The agent issues a tool call, the harness returns a result, and the model reads its whole context window to decide what to do next. My harness can't hold that call open, so "wait" is implemented as a loop that yields back to the model every so often, and the model has to choose to wait again. Each yield is a full trip through the context window. Even with 97% cache hits, that adds up: this spawn took 5.5M input tokens to coordinate two children.

Worse, every re-entry is another chance to do something other than wait. Read a file. Check a status. Peek at a transcript. The instruction said "you MUST run: meridian spawn wait," and the model still had to make that choice fresh each time. Given a big context window and a turn to fill, models find something to do.

This isn't Codex's fault. Claude Code's tool-call model makes blocking waits natural. Codex's doesn't, and I hadn't built the workaround.

The prompt fixes helped enough that I thought the problem was handled. They can't close it. As long as the harness keeps handing the turn back to the model, the model keeps getting chances not to wait. If waiting matters, the system should do the waiting.

## What I Changed

After this audit I moved qa-lead's default from GPT 5.4 on Codex to Sonnet on Claude Code. I haven't run the clean A/B yet (same qa-lead task, same inputs, different harness), so this is a bet on the failure mode: if the expensive part was re-entering the model to wait, a harness with a native blocking wait should remove it.

## What I'm Building Next

The real fix belongs in the harness. Today `meridian spawn wait` is a CLI polling loop: it watches spawn state and yields a checkpoint to the parent while children are still running. Each checkpoint re-enters the parent model.

The streaming backends already keep live executions around: Codex through its `app-server` WebSocket, OpenCode through HTTP/SSE, and Claude Code through `stream-json`. So Meridian can hold the wait itself. It watches the child spawns and, when they finish, injects the result into the parent as its next user message. No polling loop in the parent's context, and no turns handed back to the model just so it can decide to keep waiting.

That removes the re-entry that made the Codex qa-lead expensive. Whether the qa-lead actually gets cheaper still needs a clean run.

## The Bill a Subscription Hides

With the parser open, I ran it over everything. Across 10,895 sessions in three months, my agent work would have cost about $17,200 at API rates. I didn't pay that; it ran through a mix of subscriptions with changing limits. But it's a useful number to know when one night can eat half a plan.
