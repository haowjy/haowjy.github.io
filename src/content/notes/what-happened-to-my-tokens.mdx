# What Happened to My Tokens?

The codex $200 plan (20x) was so freeing. For the past few weeks, I'd barely be able to use half. However, one night, as I swapped over the full workflow to Codex, 50% of it was gone overnight.

I'm building [meridian-cli](https://github.com/haowjy/meridian-cli), a multi-agent orchestration engine that sits on top of Claude Code, Codex, and OpenCode. Agents spawn agents: a product lead spawns a tech lead, which spawns coders, reviewers, and smoke-testers. Each spawn gets a fresh context window. For this job, a major architecture refactor, meridian-cli ran 198 spawns over about eight hours while I slept.

The next morning, my Codex usage had dropped from about 60% remaining to about 10%.

That drop is what made me pull the session data apart. I wrote analysis scripts to read tool-call history from agent sessions and estimate cost per spawn. Three spawns jumped out: all qa-leads, all on Codex, all disproportionately expensive for the work they did.

## What I Tried First

My first suspicion was the explorer layer.

That was the visible problem. Explorers were supposed to be cheap reading agents, but some of them were compacting repeatedly, losing their working state, and returning reports that looked incomplete. If the reading layer can't retain the result of its own exploration, the whole delegation model gets expensive.

I tried two fixes there.

First, I changed the explorer process: start from synthesized project knowledge before opening raw source. I already had a KB for this. It covered architecture, module contracts, rationale, and decisions. The qi-layer was a different delivery mechanism: `AGENTS.md` and `.context/CONTEXT.md` files colocated with the code, so the relevant context could be surfaced during normal filesystem traversal.

I'm not sure qi was essential. A better explorer prompt that pointed at the KB first might have produced the same improvement. The measured change was narrower: this explorer stopped starting cold from source.

The result looked good. A previous explorer run cost more and churned through compaction. The new run cost `$0.11`, did not compact, and produced a better report. That comparison is also too clean. Some cost moved upstream into maintaining the inline context. In this work item, the code-mirror agents cost another `$0.66`, so the fairer comparison is closer to the old explorer plus overhead versus `$0.77` for the new setup. Still cheaper, but not a free lunch.

Second, I reread the explorer agent description and tightened the scope. The description now says to keep each explorer spawn to one module or one question. Cheap reading agents only stay cheap when the task is narrow enough for the smaller model to keep the relevant context in view. Broad "go understand this area" prompts were exactly how the explorer layer turned into compaction churn.

I also knew qa-lead was a suspect. Codex orchestrators had done this before: spawn a child, then keep poking around instead of waiting cleanly. That was why the spawn instructions had become so blunt. `meridian-spawn` told agents that every background spawn must be drained with `meridian spawn wait`, and that when wait yielded they should call wait again immediately.

I thought those changes were enough: cheaper explorer, tighter scope, explicit wait discipline. So when the explorer still looked expensive, I focused there first.

The explorer did its part. It finished in 265 seconds with a comprehensive KEEP/DELETE report for all 6 test files. The qa-lead -- after the system told it "you MUST run: meridian spawn wait" -- read the same files itself, pulled the explorer's full 51,000-token session transcript instead of the 2,000-token structured report, then wrote a cleanup strategy that closely mirrored what the explorer had already recommended.

## What I Changed Next

After this audit, I changed qa-lead's default: Sonnet on Claude Code instead of GPT 5.4 on Codex. I don't have the clean A/B run yet -- same qa-lead task, same inputs, different harness -- so I shouldn't pretend this chart proves the replacement. It was a hypothesis based on the failure mode: if the expensive part was repeated wait re-entry, a harness with native blocking wait should remove that tax.

Same work item, different role. The tech-lead ran on Claude, coordinated 10 child agents across 5 implementation phases, caught findings, ran a corrective phase, and shipped for $3.27. The qa-lead ran on Codex, coordinated 2 children, and cost $3.18. Five times the coordination for nearly the same price. That is not a controlled comparison -- tech-lead and qa-lead were doing different jobs -- but the asymmetry is hard to ignore. At minimum, the Claude run showed what efficient coordination looked like when waiting was actually blocking.

The difference is how the harness handles waiting. When a Claude Code agent calls `spawn wait`, it blocks -- one tool call, the agent sleeps, one result when the child finishes. When a Codex agent does the same thing, my harness can't truly block. Codex's interaction model is request-response: the agent issues a tool call, the harness sends the result, the model processes the full context window and decides what to do next. To implement "wait," meridian yields control back to the session periodically, and the model has to re-enter and decide to keep waiting. Each yield is a full context-window round-trip. Even with 97% cache hits, 15 yields at 5.5M tokens each is real money.

And every re-entry is a chance for the model to do something other than wait. Read a file. Check a status. Peek at a transcript. The system said "you MUST run: meridian spawn wait" -- but every time the harness yielded, the model had to choose again, and models will always find something to do with their context window.

This isn't Codex's fault. It's a gap in my harness. Claude Code's tool-call model happens to make blocking waits natural. Codex's doesn't, and I hadn't built the workaround yet.

## The Takeaway

You can't always prompt your way into reliable orchestration. The spawn instructions were explicit: after `--bg`, wait; when wait yields, re-enter wait immediately. That reduced the problem enough that I thought it was handled. This transcript showed the limit of that approach. As long as the harness keeps re-entering the model, the model gets another chance to do something that is not waiting.

For today's models, reliability has to live partly in the harness. If waiting matters, the system should wait -- not ask the model to remember to keep waiting.

## What I'm Building Next

The Codex wait problem has a real systems fix. Today, `meridian spawn wait` is a CLI polling loop: it watches spawn state, then yields a checkpoint back to the harness when children are still running. That checkpoint re-enters the parent model, and the model has to choose to call `meridian spawn wait` again.

The streaming backends already keep live executions around: Codex through its `app-server` WebSocket, OpenCode through HTTP/SSE, and Claude Code through `stream-json`. The missing piece is to move the wait barrier into Meridian's runtime. Instead of returning checkpoint messages to the model, Meridian can watch child spawns itself and inject the completed wait result into the parent execution as the next user message. No repeated model re-entry, no polling loop in the parent context, no context-window cycling just to keep waiting.

That would eliminate the polling version of the harness tax. Whether the moved qa-lead actually gets cheaper still needs a clean run. The claim I can make now is narrower: this fix removes the repeated model re-entry that made the Codex qa-lead so expensive.
