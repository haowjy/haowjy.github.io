# Finding the Evidence Was the Easy Part

I wanted to know whether a language model could get better at memory the way people do: sleep on what happened, reorganize it, and wake up knowing roughly where things are, without trying to memorize every fact.

The plan was a ladder of what I called **layered latent memory grafts**: small trainable modules on a frozen model (LoRA adapters first, then sparse memory slots or representation-level interventions if those did better). Exact facts would stay in an external retriever. The grafts would learn the fuzzy part: which project a question belongs to, which version of a fact is current, when to go look something up.

Before training anything, I needed a floor. If plain retrieval already solves the task, there's nothing for a memory graft to do. So the first phase measured retrieval on a corpus where facts change over time.

That phase is the only one that ran. Its result changed what I'd try next.

## The setup

The benchmark is [TemporalWiki drift (easy)](https://huggingface.co/datasets/saxenan3/temporalwiki-drift-cl-easy), built from TemporalWiki ([Jang et al., 2022](https://arxiv.org/abs/2204.14211)). It's a versioned wiki: about 1,004 document slices, each one a version of an article with `first_edited` and `last_edited` dates. Questions come in two splits: `test` asks about facts that changed (acquisition), and `stable` asks about facts that didn't (retention).

That versioning is why I picked it. A question carries an as-of date, so the scoring can tell apart two different successes:

- **Subject recall@5**: one of the top five results is about the right entity.
- **Temporal recall@5**: one of the top five is the right entity *at the right time*, the version whose `last_edited` matches the question's date.

A retriever can nail the first and fail the second. That gap is what stale memory looks like.

The model was `google/gemma-4-E4B-it`, run in May and June 2026. I compared two kinds of cells:

- **Harness cells**: a fixed retrieval pipeline (BM25 keyword search, or hybrid BM25 plus dense embeddings) hands the top results to the model.
- **Agent cells**: the model drives retrieval itself through tools, either a shell with `rg` or a `search_hybrid` tool that wraps the hybrid retriever.

Each run logged the agent's full tool trace and scored the final answer against the gold `object` of the question. Two earlier shakedown runs used a broken index that collapsed versions into about 329 documents. I threw those out; their numbers aren't comparable.

Give the agent a good search tool and it finds the right document, from the right date, almost every time.

The shell agent is the interesting row. On `test` it finds the right article 84% of the time but the right *version* only 65% of the time. Grepping a wiki dump finds the entity; it doesn't know which edit was current on the date in the question. That's the stale-fact failure in miniature, and the hybrid tool mostly removes it.

## But the answers are wrong

I re-ran the hybrid agent with a 16-step budget (v3). Retrieval held: temporal recall@5 of 0.95. Then I looked at the answers.

The evidence was in front of the model 95% of the time. Its answer matched exactly about 21% of the time.

Exact match is strict: an answer worded differently from the gold string counts as a miss, so some of that gap is scoring. But a 74-point gap is too big to be only wording. Most of the time the model had the right page and still didn't produce the right fact.

One ablation changed how the agent reads what it retrieves: documents in pages instead of whole. Exact match went to about 18%. Paginated reading didn't help.

## What that means

The bottleneck is using evidence, not finding it.

That matters for the memory idea, because the grafts were pitched as helping the model "know where to look." On this benchmark, the model already knows where to look. A hybrid retriever gets it to the right version of the right article. What fails is the step after: pick the right passage, scope it to the question's date, pull out the fact, and say it in the form the question asked for.

A memory module that improves recall can't move this number much, because recall is already at 95%. Whatever gets trained first should target the reading-and-answering step.

That's what the next phase was always supposed to be, though I'd framed it as a stepping stone. The first adapter in the plan was a **protocol LoRA**: an adapter trained on retrieval and answer traces (search, inspect, scope by date, answer with a citation, or defer when the evidence isn't there), not on the corpus itself. The Phase 0 result turns it from a stepping stone into the main question. If a protocol adapter can't close part of the 95-to-21 gap, nothing further up the ladder is worth building on this benchmark.

## What didn't run

Phase 1, a QLoRA protocol adapter (P1-02), is wired in the harness and has never run. Nothing past it started.

So there are no adaptation results here, and no latent-memory results. Everything below is a plan, not a finding.

Two rules from the original design carry over.

**Exact evidence stays external.** The worst outcome for a memory system isn't forgetting. It's remembering confidently without checking. Every step has to be scored on whether answers stay supported by retrieved sources, not only on whether they're right.

**The simple baseline gets the first shot.** If a rank-matched single LoRA does as well as a stack, the stack is overbuilt. If [sparse memory finetuning](https://arxiv.org/abs/2510.15103) or [representation finetuning](https://arxiv.org/abs/2404.03592) beats adapters on temporal tasks, LoRA should stay as the protocol layer and nothing more.

The closest outside work is MeMo ([arXiv:2605.15156](https://arxiv.org/abs/2605.15156)), which trains a separate memory model and leaves the base model untouched. The grafts idea put memory inside the base model's computation instead, with retrieval holding the exact facts. Phase 0 doesn't say which is better. It says neither should be judged on recall alone.
