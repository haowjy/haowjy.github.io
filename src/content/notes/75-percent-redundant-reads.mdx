# 75% of LLM Reads Are Redundant

I've been running AI coding agents heavily since February: Claude Code, Codex, OpenCode, plus a [multi-agent orchestration engine](https://github.com/haowjy/meridian-cli) I built on top of all three. After a [particularly expensive overnight session](/notes/what-happened-to-my-tokens), I wanted to understand my usage at scale. Not just one bad spawn. Everything.

I wrote a script that pulls tool-call history from every session across all three harnesses. Claude Code stores sessions as JSONL. Codex has its own event format. OpenCode writes to SQLite. The script normalizes all three and extracts every file read: `Read` tool calls, `cat` and `sed` in bash, `grep` and `rg`. Then it checks whether the agent had already seen that file earlier in the same session.

The dataset covers 4,339 sessions from February through May 2026, across a dozen models, three harnesses, and 30+ agent roles.

<FigureLead value="75.1%" label="of file reads were redundant" detail="50,319 of 67,017 reads across 4,339 sessions" />

Three out of four file reads were repeats. The agent read a file, kept working, then read the same file again later in the same session.

## Where the repeats come from

**Read-edit-reread** is the biggest source. An agent reads a file, edits it, reads it back. I found 2,197 read-after-edit events across the dataset. The worst single session had 76.

**Delegation restarts context.** My setup spawns agents from agents, and each spawn starts with a fresh context window. The parent already read the files and knows what matters; the child starts blind and reads them again. Some of that is the price of delegation. The open question is how much a better handoff (file contents passed in the spawn, or prewritten `.context/` notes) would save.

**Compaction creates amnesia loops.** The agent fills its context, compacts it into a lossy summary, forgets the file contents, re-reads them, and fills the context again. Sessions that compacted averaged 67 reads and cost $20.16. Sessions without compaction averaged 13 reads and $1.13. One session compacted 29 times.

The spread tracks the role, not the model. GPT-5.4 was my leaf coder and reviewer: reading, editing, and re-reading all day. GPT-5.5 was my orchestrator, and orchestrators delegate instead of reading. GPT-5.4-mini was my explorer, which reads files, writes a report, and stops. Redundancy follows how much editing a role does.

The explorer number still stood out. 42% is high for a role that should read once and report. When I dug in, the cause was compaction: explorers filled their context, compacted, lost the files they had read, and read them again. That's what led me to build `.context/CONTEXT.md` files: prewritten notes colocated with the code, so an explorer can understand a module from a few hundred lines of markdown instead of 20 source files. I also started scoping each explorer to a single question and fanning out several cheap spawns instead of one that reads everything. Both changes cut the compaction-driven re-reads significantly.

Codex agents had zero explicit re-reads, but 5 inline verifications (a read-back inside the same bash command) and 14 `git diff` checks. Claude agents re-read after 5 of 42 edits and ran tests 10 times. Both verify their edits. They use different mechanisms. Claude Code's separate `Read` and `Edit` tools make verification a distinct tool call that my analyzer counts. Codex edits through bash, so verification hides inside the same command or a `git diff`, where a tool-call parser can't see it.

A `git diff` after 12 edits is one command. Twelve `Read` calls after twelve `Edit` calls is 24 tool round-trips. The tool interface shapes what you can measure as much as what agents do.

What the data does show: no model, on any harness, in any role, drops below 30% redundancy. The best case still re-reads about a third of its files.

Anthropic noticed the pattern too. Recent versions of Claude Code's Read tool inject an instruction not to re-read a file right after editing it, since Edit would have errored if the change failed. I found it in the [tracked system prompt history](https://github.com/Piebald-AI/claude-code-system-prompts). It's injected through a template variable (`ADDITIONAL_READ_NOTE`) made configurable in v2.1.91 on April 3, 2026, so it may be model-dependent or feature-flagged, and I can't tell which of my sessions had it.

RAE only measures what it claims to on Claude Code, so that's where I tested it. I cut the Claude Code data at the v2.1.91 release date:

## What I'd do about it

Prompting against re-reads hasn't clearly worked, and some re-reading is reasonable: an agent that just edited a file wants to know what's in it now. The waste is in where the file contents live. Every read appends another full copy of the file to the conversation, compaction throws those copies away, and the agent reads the file again.

I think the harness should hold the current contents of active files and stop storing them as transcript history. I wrote that up as a proposal, with prior work and an experiment design, in [A working-memory cache for agent file reads](/notes/working-memory-cache).

<Callout type="note" eyebrow="METHODOLOGY">
"Redundant" means the agent read a file it had already read earlier in the same session, counted at the tool-call level. It doesn't weight partial re-reads, and it misses verification inside compound bash commands, which is why the RAE split between harnesses is partly an artifact. Costs apply published API pricing to actual token counts; subscription plans hide real cost. An earlier version of this post double-counted Codex cache-read tokens; the costs above are corrected. Read counts and redundancy rates were unaffected. Scripts, the time-series tracker, and the April 3 cut are on [GitHub](https://github.com/haowjy/datadump/tree/main/where-my-tokens-went).
</Callout>
